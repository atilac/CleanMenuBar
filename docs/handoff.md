# Where things stand

Written 25 September 2026, with CleanMenuBar 0.1.3 waiting for App Store review.
The point of this file is that the next person to pick this up — including a
future me — should not have to reconstruct any of it.

## The one thing that is pending

**App Store review of 0.1.3.** Submitted 25 September 2026, 13:43 BRT, state
`WAITING_FOR_REVIEW`, release type `AFTER_APPROVAL` — so it publishes itself the
moment it clears. Review usually takes one to three days.

Nothing else is blocked on anything.

## What to do when it is approved

1. **Turn the store button on.** In `Tools/build-site.py`, `SHOW_APP_STORE` is
   `False`. Flip it, run `python3 Tools/build-site.py`, then
   `bash Tools/deploy-site.sh`. The button is already built and translated into
   all nine languages, and it already says *buy* rather than *download* —
   correct, because the listing went out at US$ 0.99.
2. **Check the link resolves.** It points at
   `https://apps.apple.com/app/id6815842748`, which is the real id but returns
   nothing until the listing is live.
3. **Consider the Homebrew cask**, which has never been set up.

## What to do if it is rejected

The likeliest objection is the hiding technique itself. It uses only public
`NSStatusItem` API and stays inside the sandbox, but macOS 27 shipped no
supported API for menu bar management, so a reviewer could still take issue.
Distribution outside the store via Developer ID is unaffected either way — the
GitHub release is signed, notarised and already public.

The reviewer notes were written precisely to head off the other likely
rejection: an app that appears to do nothing. They are in App Store Connect and
in `app-store-submission.md`, and they spell out the ⌘-drag step.

## Things that cost time and should not cost it twice

**The API key is two keys.** `ABX25DD23T` is read-only and notarises in CI;
`H62S9X5DTG` is App Manager and does everything else. Neither is named after a
project because neither is scoped to one. They live in
`~/Developer/CleanMenuBar-signing/`, a directory whose name is a leftover —
nothing in it is specific to this app, and moving it somewhere team-shaped is
still worth doing before the next product needs it.

**App Store Connect will not say why a submission is invalid.** The API returns
`This resource cannot be reviewed, please check associated errors` and nothing
else. The web interface names the missing field outright. When the submission
refuses, open the version page and read the red box rather than guessing —
guessing cost four rounds here.

The four fields that were missing, none of them obvious: version **Copyright**,
the **age rating** declaration, **content rights**, and **App Privacy**, whose
answers were filled in but left unpublished. A draft App Privacy reads as
missing, not as draft.

**The listing text lives in the repository**, in `docs/app-store/*.md`, and
`Tools/push-app-store-metadata.py` pushes it. Fixing a typo is a diff and a
command, not nine web forms. `Tools/push-app-store-screenshots.py` does the same
for images. Two things they had to learn the hard way: App Store Connect rejects
`<` and `>` in a description as markup, and creating a name localisation
silently creates the description localisation too.

**The site is built, not edited.** `site/` is generated by
`Tools/build-site.py` from `Tools/site_content.py`; `site/style.css` is the one
handwritten file in there. Editing the generated HTML loses the edit on the next
build.
